# MoSJE Product 2 – Integration Specification (API v1)

**Scholarship Discovery Assistant – WhatsApp + web companion**
Version 1.0 · 28 Sep 2026 · Rule version: Scholarship Eligibility Rule V3.0 · Status: prototype (synthetic / test data only)

This document is the contract between **Product 2** (this service) and any **Product 1** system (the record-linkage and eligibility platform). Two Product 1 builds exist in parallel (for example `p1-rajat` and `p1-teamB`). Both connect in the same way. Product 2 does not import or depend on any Product 1 code.

## 1. What Product 2 does

1. A Product 1 **pushes referrals**: students it wants to reach (for example PROBABLE-band records that could not be linked, or linked students with no shortlist), with whatever facts it already knows.
2. A Product 1 **registers its outreach messages** (SMS, WhatsApp or email) and gets **trackable links** to put in them.
3. The student chats with the assistant on **WhatsApp** or in the **web companion**. The bot asks only the facts the V3.0 rule needs and are still missing, runs Product 2's own copy of the eligibility engine against the 547-row scheme master, and shows schemes the student can explore, with where to apply.
4. The student can rate the service and gets a **personal share link** for friends.
5. The Product 1 **pulls results** (`GET /v1/results`) or receives them by **callback**. Each result says which channel was used, how the student arrived (entry source) and which schemes were suggested.

```text
 Product 1 (p1-rajat)          Product 2 (this service)                  Student
 ────────────────────          ─────────────────────────                 ───────
 POST /v1/referrals      ───►  referrals (per source_system)
 POST /v1/outreach-messages ─► OM code + links  ──── link in SMS ──────► taps link
                                                 ◄── WhatsApp / web chat ─┘
                               conversation engine (channel-agnostic)
                               + eligibility engine (Rule V3.0, 547 schemes)
 GET /v1/results         ◄───  results (answers, schemes, entry source)
 callback (optional)     ◄───  POST discovery.result
```

**Important wording rule.** Results are "schemes you can explore based on the student's own answers". They are not an eligibility decision. The final decision is always made by the scheme's department.

## 2. Base URL and versioning

* Base URL: `https://<service>.onrender.com` (for example `https://mosje-p2-api.onrender.com`). Ask the Product 2 owner for the exact URL.
* All integration endpoints are under `/v1`. Fields may be **added** to responses in v1. Existing fields will not be renamed or removed without a new version (`/v2`). Clients must ignore unknown fields.
* Interactive documentation (OpenAPI/Swagger): `GET /docs`. Machine-readable schema: `GET /openapi.json`.
* Health: `GET /health` (no key needed).
* All timestamps in the API are **UTC, ISO-8601 with a `Z`**, for example `2026-10-01T04:00:00.000000Z` (= 09:30 IST). Inputs may carry any offset, for example `2026-10-01T09:30:00+05:30`.
* Free hosting sleeps after 15 minutes without traffic. The first call after a pause can take up to about 1 minute. Use a 90-second timeout and retry once.

## 3. Authentication and tenancy

Every `/v1` call (except public web-chat sessions, section 6) needs an API key in the header:

```http
X-API-Key: <your key>
```

`Authorization: Bearer <your key>` is also accepted.

| Key type | Configured by | Can do |
|---|---|---|
| **Source-system key** (recommended) | `P2_API_KEYS="p1-rajat:KEY1,p1-teamB:KEY2"` on the Product 2 server | Acts only as its own `source_system`. It cannot read or write another source system's referrals, outreach messages or results. |
| **Admin key** | `P2_API_KEY` (generated by Render) | Can act for any source system by naming it (`source_system` in the body or query). Opens the admin page. Needed for `/whatsapp/send-template`. |

* `source_system` is a short identifier for each Product 1: letters, digits, `.`, `_`, `-`, maximum 64 characters. Examples: `p1-rajat`, `p1-teamB`.
* With a source-system key you may leave `source_system` out; it is filled in from the key. If you send a different value you get `403 forbidden_source_system`.
* With the admin key, a missing `source_system` means `default`.
* Keys are secrets. Keep them on your server. **Never put an API key in browser JavaScript or a mobile app.**

## 4. Referral fields

A referral is one student that a Product 1 wants Product 2 to reach. It is identified by **(`source_system`, `external_ref`)**. Posting the same pair again **updates** the referral (upsert); known facts are merged.

| Field | Type | Required | Notes / allowed values |
|---|---|---|---|
| `external_ref` | string ≤100 | **yes** | Your own opaque ID for the student (for example `P1-STU-000123`). Do **not** use Aadhaar, Jan Aadhaar or roll numbers. |
| `source_system` | string ≤64 | no | Taken from your key. Only with the admin key. |
| `mobile` | string | recommended | 10-digit Indian mobile (`9876543210`) or with country code (`+91 98765 43210`). Stored as digits with country code (`919876543210`). Needed to recognise the student on WhatsApp. |
| `name` | string ≤200 | no | Used only for the greeting ("Namaste Aarav!"); only the first name is shown. |
| `state` | string | no | State/UT of domicile. Canonical names as in `GET /v1/meta` (`Rajasthan`, `Delhi`, `Dadra & Nagar Haveli and Daman & Diu` …). Common aliases (NCT of Delhi, Orissa, UP) are accepted. |
| `class_passed` (alias `class`) | string | no | `X` or `XII` (also `10`, `12`, `Class 10`). Used for the Education Stage check. |
| `category` | string | no | `SC`, `ST`, `OBC`, `General`, `Minority` (`Gen` is accepted). |
| `gender` | string | no | `Male`, `Female`, `Transgender` (`M`/`F`/`T` accepted). |
| `annual_family_income` (alias `income`) | integer (₹) | no | Annual family income in rupees. `180000`, `"1.8 lakh"`, `"₹1,80,000"` are accepted. |
| `dob` | date | no | `YYYY-MM-DD` (or `DD-MM-YYYY`). Stored; used only if a scheme has a computable age rule (none in the current V3.0 master). |
| `disability` | boolean | no | `true`/`false`/`yes`/`no`. Stored and returned. **Not evaluated** (V3.0 does not evaluate disability). |
| `reason` | string ≤50 | no | Why you refer the student. Standard values: `PROBABLE` (linkage score 70–89.99, not linked), `UNLINKED`, `MATCHED`, `NO_SCHEMES`, `OTHER`. Other values are stored with a warning. |
| `language` | string | no | `en` or `hi`. If set, the bot skips the language question. |

**Facts and pre-filling.** Known facts are shown to the student for confirmation ("From your records we already have: … Is this correct?"). If the student says yes, those questions are skipped. If no, all questions are asked. A value that cannot be recognised is dropped and reported in `warnings`; the student will simply be asked.

**PROBABLE records.** Per Record Linkage Rules V3.0, PROBABLE-band records are not linked, so **send only facts from the CBSE record** (name, mobile, class passed, and state if it comes from the school). Do not send Jan Aadhaar attributes for them.

## 5. Endpoints

### 5.1 `POST /v1/referrals` – push a batch

Request:

```json
{
  "source_system": "p1-rajat",
  "referrals": [
    {"external_ref": "P1-STU-0001", "mobile": "9876500001", "name": "Aarav Sharma",
     "state": "Rajasthan", "class_passed": "X", "category": "SC", "gender": "Male",
     "annual_family_income": 180000, "reason": "PROBABLE", "language": "en"},
    {"external_ref": "P1-STU-0002", "mobile": "9876500002", "name": "Priya Meena",
     "state": "Rajasthan", "class_passed": "XII", "reason": "UNLINKED"}
  ]
}
```

`source_system` at the top is optional (default for items that do not have one). Maximum 5,000 items per call.

Response `200`:

```json
{
  "received": 2, "created": 2, "updated": 0,
  "rejected_count": 0, "rejected": [],
  "warnings": []
}
```

Each invalid item is rejected on its own with its index, for example `{"index": 2, "external_ref": "P1-STU-0003", "errors": ["mobile '12345' is not a valid number ..."]}`. Valid items in the same batch are still saved.

curl:

```bash
curl -X POST "$P2/v1/referrals" -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"referrals":[{"external_ref":"P1-STU-0001","mobile":"9876500001","name":"Aarav Sharma","state":"Rajasthan","class_passed":"X","category":"SC","reason":"PROBABLE"}]}'
```

### 5.2 `POST /v1/referrals/upload` – CSV or XLSX

Multipart form: `file` (required, `.csv` or `.xlsx`, maximum 5 MB), `source_system` (optional, admin key only). The first row holds the column names, which are the same as the JSON field names. Template: `templates/referrals_template.csv`. The response is the same as 5.1, plus `file`.

```bash
curl -X POST "$P2/v1/referrals/upload" -H "X-API-Key: $KEY" -F "file=@referrals.csv"
```

### 5.3 `GET /v1/referrals/{external_ref}` – one referral and its latest result

Query: `source_system` (admin key only). Response: the referral (`status`, `known_facts`, `mobile_masked`, `invite_status`, `callback_status`, timestamps, `sessions_count`) and `latest_result` (the result object, section 8).

```bash
curl "$P2/v1/referrals/P1-STU-0001" -H "X-API-Key: $KEY"
```

### 5.4 `POST /v1/referrals/{external_ref}/invite` – send a WhatsApp template (optional)

Sends an approved WhatsApp template to the referral's mobile. Body (all optional):

```json
{"template": "scholarship_discovery_invite_en", "language": "en", "params": ["Aarav", "X"]}
```

The default template is `WHATSAPP_INVITE_TEMPLATE` (`hello_world`, the only template available on Meta's free test number). For templates other than `hello_world`, `params` defaults to `[first_name, class_passed]` (matching the draft Discovery template in Record Linkage Rules V3.0). Returns `invite_status`. Returns `409 opted_out` if the student replied STOP. With a Meta **test** number, messages reach only the (up to 5) verified recipient numbers.

### 5.5 `GET /v1/results` – pull results

Query parameters:

| Param | Meaning |
|---|---|
| `since` | ISO-8601 time. Returns sessions **updated after** this time. Use the `next_since` value from the previous response. |
| `status` | `ACTIVE`, `COMPLETED`, `OPTED_OUT`, `RESTARTED` |
| `channel` | `whatsapp` or `web` |
| `entry_source` | `OUTREACH`, `ORGANIC`, `PEER_REFERRAL` |
| `source_system` | Admin key only. `walk-in` = sessions not tied to any source system. |
| `limit` | 1–500, default 100 |

Response:

```json
{"count": 1, "next_since": "2026-10-01T04:12:09.123456Z", "has_more": false, "results": [ { "...": "result object, section 8" } ]}
```

Polling pattern: store `next_since`; call again with it; if `has_more` is true, call again straight away. One session appears again each time it changes (for example ACTIVE, then COMPLETED), so upsert by `session_id`.

```bash
curl "$P2/v1/results?since=2026-10-01T00:00:00Z&status=COMPLETED" -H "X-API-Key: $KEY"
```

A session belongs to a source system when it is linked to one of its referrals, started from one of its outreach links, or created with its key (web). Sessions that started organically, or from a peer's share link, with no referral match are **walk-ins** and are visible only with the admin key.

### 5.6 Callbacks – `GET/PUT /v1/source-systems/me`

Register an HTTPS URL to receive results as soon as a session completes (or the student opts out):

```json
PUT /v1/source-systems/me
{"callback_url": "https://p1.example.org/p2/callback", "callback_secret": "at-least-16-characters-secret"}
```

`GET /v1/source-systems/me` shows the URL, whether a secret is set, and your referral counts by status. Send `{"callback_url": null}` to stop callbacks.

Product 2 then sends:

```http
POST https://p1.example.org/p2/callback
Content-Type: application/json
X-P2-Signature: sha256=<hex HMAC-SHA256 of the raw body, key = callback_secret>

{"event": "discovery.result", "sent_at": "2026-10-01T04:12:09.500000Z", "result": { ...result object... }}
```

* Reply with any 2xx within 10 seconds. There is one attempt per event; the outcome is stored in the referral's `callback_status`. **Polling `/v1/results` stays the source of truth**, so a missed callback loses nothing.
* Verify the signature (Python):

```python
import hmac, hashlib
def valid(raw_body: bytes, header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header or "")
```

### 5.7 `POST /v1/discover` and `GET /v1/meta`

* `POST /v1/discover` is stateless: send facts, get schemes back. It stores nothing. Body: `state`, `class_passed`, `category`, `gender`, `annual_family_income`, `dob`, `limit` (1–200, default 10), `include_audit` (true = per-scheme PASS/FAIL for all six checks).
* `GET /v1/meta` returns the controlled values: states, categories, genders, classes, referral fields, entry sources, the questions the bot asks, scheme counts and the WhatsApp number (if known).

```bash
curl -X POST "$P2/v1/discover" -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"state":"Rajasthan","class_passed":"X","category":"SC","gender":"Male","annual_family_income":180000,"limit":5}'
```

## 6. Web channel and embeddable companion

The conversation engine is **channel-agnostic**. The same dialogue, state machine and eligibility logic serve WhatsApp and the web; only the adapter differs. Web replies are structured JSON (text, quick-reply options, scheme cards).

### 6.1 Chat API

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /v1/chat/sessions` | `X-API-Key` **or none** (public, if `COMPANION_PUBLIC=true`) | Start a session. Body: `external_ref` (key needed, pre-fills from that referral), `language` (`en`/`hi`), `entry` (attribution params, section 7). Returns `session_id`, `session_token`, `companion_url`, `entry_source` and the first `reply`. |
| `POST /v1/chat/sessions/{id}/messages` | `X-Session-Token` (or the owning `X-API-Key`) | Body `{"text": "..."}`: an option `id` (for example `"2"`) or free text. Returns `reply`, `status`, and `session_id`. If `new_session` is true (after restart), use the new `session_id`; the same token keeps working. |
| `GET /v1/chat/sessions/{id}` | same | Result object, transcript and `last_reply` (to resume a widget). |

Reply object:

```json
{
  "text": "Based on your answers, here are 5 scholarship(s) you can explore (showing 1–5 of 11):",
  "options": [{"id": "1", "label": "Show more schemes"}, {"id": "2", "label": "Rate this service & get your share link"},

             "benefit": "Academic allowance ...", "apply_url": "https://scholarships.gov.in/"}],
  "footer": "ℹ️ This list is based only on your answers ... Final eligibility is decided by the scheme's department.",
  "state": "RESULTS", "status": "COMPLETED", "language": "en", "input_hint": "choice",
  "share": null

```

`input_hint` is `choice` (show buttons), or `text` (also allow typing: state name, income amount, comment). `share` carries `share_code`, `web_link`, `whatsapp_link` after feedback.

### 6.2 Embedding the companion in a Product 1 web app

| Option | How | Notes |
|---|---|---|
| A. Floating button | `<script src="https://<service>.onrender.com/companion/embed.js" defer></script>` | Adds a "🎓 Find scholarships" button and a chat panel (iframe). Optional attributes: `data-lang="hi"`, `data-label`, `data-open="true"`, `data-session` + `data-token`, and attribution `data-src`, `data-om`, `data-r`, `data-ref`. Attribution parameters in the host page URL (`src`, `om`, `r`, `ref`, `utm_*`) are passed through automatically. JS: `window.MosjeP2Companion.open()`. |
| B. Inline iframe | `<iframe src="https://<service>.onrender.com/companion" style="width:380px;height:600px;border:0"></iframe>` | Add `?lang=hi` or attribution parameters. |
| C. Pre-filled for a known student | Your **server** calls `POST /v1/chat/sessions` with your key and `external_ref`, then puts the returned `companion_url` in an iframe (or passes `data-session`/`data-token` to embed.js). | The student is greeted by first name and asked to confirm known facts. The session counts under your source system. |
| D. Your own chat UI | Call the chat API from your front end (public sessions), or from your back end (with key). | Allow your origin in `ALLOWED_ORIGINS`. |

A live demo page is at `/companion/demo`. Try the companion at `/companion`.

**Security settings (server env vars).**
`ALLOWED_ORIGINS` = comma-separated origins (for example `https://p1-rajat.onrender.com,https://p1-teamb.example.org`). It enables CORS for those origins (option D) and restricts which sites may frame `/companion` (CSP `frame-ancestors`). Empty = no cross-origin API calls, and the companion can be framed anywhere (demo mode).
`COMPANION_PUBLIC=false` switches off anonymous sessions; then only option C works.

## 7. Entry-source attribution and outreach links

Every session, on both channels, records **how the student arrived** (first touch).

| `entry.source` | Meaning | How it is detected |
|---|---|---|
| `OUTREACH` | Student tapped a link in an outreach message sent by a Product 1 | WhatsApp: the first message contains a code `OM-XXXXXX` (optionally `OM-XXXXXX-RXXXXXXXX`). Web: `/companion?src=outreach&om=…` (or `utm_campaign=<OM code>`). |
| `PEER_REFERRAL` | Student came from another student's share link after that student gave feedback | WhatsApp: the message contains `REF-XXXXXX`. Web: `/companion?src=referral&ref=REF-XXXXXX`. |
| `ORGANIC` | Student found the bot on their own | No code or parameters. `entry.channel` tells `whatsapp` or `web`. `utm_*` parameters, if any, are still recorded. |

A message that contains a code always starts a **fresh, attributed** session, even if the student was in the middle of another chat. A restart keeps the original attribution (`first_touch.inherited_from`). Unknown codes still count as `OUTREACH`/`PEER_REFERRAL`, with `first_touch.resolved = false`.

### 7.1 Register an outreach message – `POST /v1/outreach-messages`

```json
{
  "message_id": "2026-10-01-probable-wave1",
  "campaign": "PROBABLE discovery – Rajasthan – wave 1",
  "channel": "sms",
  "template_text": "Namaste {{name}}, find scholarships you can explore: {{link}} Reply STOP to opt out.",
  "template_version": "discovery_invite_sms_v1",
  "sent_at": "2026-10-01T09:30:00+05:30",
  "recipients": ["P1-STU-0001", "P1-STU-0002"]
}
```

| Field | Type | Notes |
|---|---|---|
| `message_id` | string ≤100, required | Your ID for this message/wave. Unique per source system. Re-posting updates it (the code stays the same). |
| `campaign` | string ≤200 | Human-readable campaign name. |
| `channel` | `whatsapp` \| `sms` \| `email` | The channel **your** message goes out on. |
| `template_text`, `template_version` | string | For audit: the exact text/version sent. |
| `sent_at` | ISO-8601 | When you sent it (stored in UTC). |
| `recipients` | list of strings, optional (≤5,000) | Usually your referral `external_ref`s. Each gets its own opaque code, linked to the referral if one exists. More can be added later with `POST /v1/outreach-messages/{message_id}/recipients` `{"recipients": [...]}`. |

Response `201` (shortened):

```json

            "by_channel": {"whatsapp": 0, "web": 0}, "recipients_registered": 2},
  "recipients": [
    {"recipient_ref": "P1-STU-0001", "code": "RS5WEPER2", "referral_linked": true,
     "whatsapp_text": "Hi, I want to find scholarships. Code OM-ADN57S-RS5WEPER2",
```

### 7.2 Link formats

| Link | Format |
|---|---|
| WhatsApp, generic | `https://wa.me/<WhatsApp number digits>?text=<url-encoded "Hi, I want to find scholarships. Code OM-XXXXXX">` |
| WhatsApp, per recipient | same, with code `OM-XXXXXX-RXXXXXXXX` |
| Web, generic | `<base>/companion?src=outreach&om=OM-XXXXXX[&utm_source=…&utm_medium=…&utm_campaign=…]` |
| Web, per recipient | add `&r=RXXXXXXXX` |
| Peer share (WhatsApp) | `https://wa.me/<number>?text=<"Hi, my friend suggested this scholarship helper. Code REF-XXXXXX">` |
| Peer share (web) | `<base>/companion?src=referral&ref=REF-XXXXXX` |

Codes use the characters `A–Z` (without I, L, O) and `2–9`, and are not case-sensitive. The student may also type the code by hand. `om` also accepts your `message_id` (if it is unique), and `r` also accepts your `recipient_ref`, but **opaque codes are recommended** so that no internal IDs appear in URLs.

`<WhatsApp number>` comes from the server setting `WHATSAPP_DISPLAY_NUMBER`, or is learned from the first webhook Meta sends. Until it is known, `whatsapp_link` is `null`; `whatsapp_text` is always present.

### 7.3 How a Product 1 generates outreach links (step by step)

1. Push the referrals (`POST /v1/referrals`).
2. Register the message **before sending**: `POST /v1/outreach-messages` with `message_id`, campaign, channel, template text/version, and `recipients` = the referral `external_ref`s.
3. Put each recipient's `whatsapp_link` (WhatsApp-first) or `web_link` into that recipient's message. For bulk SMS without personalisation, use the generic `links`.
4. Send the message through your own provider (SMS gateway, WhatsApp BSP, email). Product 2 does not send your outreach.
5. Poll `GET /v1/results?entry_source=OUTREACH&since=…` and/or `GET /v1/outreach-messages/{message_id}` for click-through (sessions started) and completion.

With a Meta **test** number, only verified recipient phones can chat. Real campaigns need an approved business number and templates.

### 7.4 Feedback and peer referral

After the results, the student can choose "Rate this service & get your share link": a rating 1–5, then an optional comment (or SKIP). The bot then sends a personal share code `REF-XXXXXX` with WhatsApp and web links. Sessions started with that code are `PEER_REFERRAL`, and `entry.referrer_share_code` shows the code. The referrer's result shows `share_code`, `feedback` and `peer_referrals_count`. Restarts are not counted twice.

## 8. Result object

| Field | Type | Notes |
|---|---|---|
| `session_id` | string | Opaque (`s_…`). Upsert key. |
| `channel` | `whatsapp` \| `web` | |
| `source_system` | string \| null | null = walk-in |
| `external_ref`, `referral_reason` | string \| null | When linked to your referral |
| `status` | string | `ACTIVE`, `COMPLETED`, `OPTED_OUT`, `RESTARTED` (session replaced by a new one) |
| `state` | string | Current step: `LANG`, `CONFIRM_PREFILL`, `ASK_<fact>`, `RESULTS`, `FEEDBACK_RATING`, `FEEDBACK_COMMENT`, `ENDED` |
| `language` | `en` \| `hi` | |
| `mobile_masked` | string | For example `91••••••0001`. Full numbers are never returned. |
| `prefill_used` | boolean | The student confirmed the facts you sent. |
| `answers` | object | Facts used: `class_passed`, `state`, `category`, `gender`, `annual_family_income` (a range's upper bound, or the typed amount, or null = "don't know"). `class_passed: "OTHER"` = not a Class 10/12 pass-out (no schemes shown). |
| `eligible_count` | integer \| null | Number of schemes whose six V3.0 checks all pass for these answers |
| `suggested_schemes` | list | `rank`, `scheme_id` (`MSM-0001` … = master row), `name`, `benefit`, `apply_url`, `shown_to_student` |
| `entry` | object | `source`, `channel`, `outreach_message_id`, `outreach_code`, `campaign`, `outreach_channel`, `recipient_ref`, `referrer_share_code`, `first_touch` (raw text or URL params, `utm_*`, codes, `resolved`, `at`), `first_touch_at`. Outreach details are shown only to the source system that owns the message. |
| `feedback` | object \| null | `rating` 1–5, `comment` |
| `share_code`, `peer_referrals_count` | | |
| `rule_version`, `eligibility_as_of` | | `V3.0`, date |
| `started_at`, `updated_at`, `completed_at` | UTC | |

Referral `status` values: `RECEIVED` → `INVITED` (template accepted by Meta) → `IN_CONVERSATION` → `COMPLETED`, or `OPTED_OUT`.

## 9. Which questions the bot asks, and why

The V3.0 rule has six mandatory AND checks: Jurisdiction, Age (from DOB), Gender, Family Income, Social Category and Education Stage. Product 2 asks only what can change an outcome with the **loaded master**:

* always: class passed (X / XII → Education Stage), State/UT (Jurisdiction), social category;
* gender and income: asked because some active schemes have a parsed gender or income condition;
* date of birth: **not asked**, because no scheme in the current master has a computable age rule. (Schemes with an age condition that cannot be computed fail under V3.0 in any case.) If a future master adds computable age rules, the bot starts asking for DOB automatically.

Income is chosen from ranges (up to ₹1 lakh, 1–2.5, 2.5–3.5, 3.5–4.5, 4.5–8, above 8 lakh, don't know), or typed as an amount. The upper bound of a range is used. This is conservative, so a scheme is never shown because of rounding down. "Don't know" fails only the schemes that have an income ceiling. Only Class 10 and Class 12 pass-outs are covered, matching the V3.0 Education Stage derivation.

## 10. Errors

Errors return JSON: `{"detail": {"error": "<code>", "message": "<human text>"}}`. Request-validation errors use FastAPI's standard `422` format (`detail` is a list).

| HTTP | `error` | When |
|---|---|---|
| 400 | `invalid_source_system`, `invalid_since` | Bad parameter format |
| 401 | `missing_api_key`, `invalid_api_key`, `invalid_session_token` | No key, unknown key, wrong session token |
| 403 | `forbidden_source_system`, `admin_only` | Key used for another source system; admin-only endpoint |
| 404 | `referral_not_found`, `outreach_message_not_found`, `session_not_found` | Not found (or belongs to another source system) |
| 409 | `opted_out` | The student replied STOP |
| 413 | `batch_too_large`, `file_too_large` | More than 5,000 items / 5 MB |
| 415 | `unsupported_file_type` | Upload that is not .csv/.xlsx |
| 422 | `no_mobile` / validation | Referral without mobile for invite; malformed JSON body |
| 503 | `not_configured` | Server has no API key configured |

## 11. Limits

5,000 referrals or recipients per call; 5 MB per upload; 500 results per page; text messages up to 1,000 characters (web). Free hosting: one small instance that sleeps after 15 minutes idle. This is not for load testing.

## 12. Privacy and data protection

* **This hosting is for synthetic or test data only.** No real government personal data (CBSE, Jan Aadhaar or other departmental records) may be sent to the Render deployment or to any free database. Real data must stay on **NIC / MeghRaj** infrastructure after the MoUs, security audit and privacy review listed in the Product 2 to-do list.
* Send the minimum: an opaque `external_ref`, mobile, first name, and only the facts you need to pre-fill. Never send Aadhaar, Jan Aadhaar IDs, roll numbers, addresses or parents' names.
* Links carry only opaque codes (`OM-…`, `R…`, `REF-…`), never names or IDs. A per-recipient link greets the student by first name and shows the pre-filled facts to whoever opens it, so treat it as personal. Use generic links where that is a concern.
* Mobile numbers are masked in every API response and on the admin page. Full numbers are stored only to recognise WhatsApp users.
* Tenancy: each source-system key sees only its own data.
* STOP opts the student out: the bot stops replying, and invites are refused with `409`. Sending "hi" again opts back in.
* Retention and consent wording are still to be decided (to-do list, section 1). The prototype keeps data until the database is deleted.

1. `GET /health` → `status: ok`.

3. Push 2–3 synthetic referrals with your team's test phone numbers (must be verified recipients on the Meta test number).

5. On a verified phone, open the `whatsapp_link` → WhatsApp opens with the code pre-filled → send → chat.
6. `GET /v1/results?since=…` → your sessions, with `entry.source = OUTREACH` and suggested schemes.
